<objective>
Investigate and resolve GAP-B (from 04-VERIFICATION.md): on the test device the fired alarm did
NOT surface over a secure keyguard — the user had to unlock and tap the notification. This is a
different subsystem from GAP-A: the full-screen-intent / `showWhenLocked` path
(`AwesomeNotifications().createNotification(..., fullScreenIntent: true)` +
`FlutterShowWhenLocked().show()`), NOT the camera layout. The most likely cause is Android 14+
(API 34, the compileSdk) restricting `USE_FULL_SCREEN_INTENT` — for non-calendar/non-alarm
default apps the permission is no longer auto-granted at install and must be requested at runtime
— and/or OEM keyguard policy blocking an activity over a secure lock screen.

Purpose: An alarm that does not show over the lock screen is a weaker alarm (core value:
"reliably ring and reliably stop"). This is investigation-led: AUDIT the full path, then EITHER
fix it (request/surface the runtime permission, correct the notification config) OR document it
as expected OEM/Android-14 no-go behavior — which is acceptable per D-LOCK-SHIP because the
default-on escape hatch and the unlock-to-scan degradation already cover no-go devices. This plan
may subsume the deferred 04-03 lock-screen spike (per 04-VERIFICATION.md: "GAP-B may replace
04-03").

Output: A root-cause finding, a fix (or a documented accept) for the full-screen-intent path,
and `04-LOCKSCREEN-SPIKE.md` recording the per-device verdict.
</objective>
